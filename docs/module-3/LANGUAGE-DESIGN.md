# 语言适配与 NVIDIA 组件兼容设计

日期：2026-09-26｜状态：设计评审，尚未改动语音模块或实现翻译服务。为 [总体设计](DESIGN.md)与 [API](API.md)的 v0.3 补充。

## 1. 截图提醒了什么

用户提供的团队讨论提出了中文交互与 NVIDIA 组件适配的担忧，以及“后台英文，再由本地模型转中文”的候选方案。这里将其作为需要验证的集成条件，不把截图中的赛事语言判断视为官方规则，也不将候选方案直接当作已确定架构。原截图包含团队聊天，设计文档只记录相关问题，不复制截图或成员个人信息。

需要分别决定四件事：**老人说什么语言、系统对老人用什么语言、模型处理什么语言、API 使用什么字段名。** 英文字段名与枚举可以承载中文文本，本身不要求翻译；中文界面也不能保证底层 ASR、TTS 或安全规则已经支持中文。

## 2. 当前证据与尚未验证的部分

本地任务一快照：`origin/ziyang-module-1@d7e8cd0`。本轮只读代码及文档，没有拉取远程最新状态、加载模型或复验其历史测试。

| 层次 | 实际看到的内容 | 设计影响 |
|---|---|---|
| 配置 | `skills/elderly_voice_duplex/config.py` 默认使用 Nemotron 3.5 ASR 与 MagpieTTS | 按实际 model ID 和 checkpoint 核对，不能只写“NVIDIA SDK” |
| 提示与规则 | `prompts.py` 中的主提示、犹豫词与安全匹配规则为英文 | 中文切入前需要对应语言的规则与用例，不能只翻译最终回复 |
| TTS 适配 | `adapters/nemo_tts.py` 的 tokenizer 仍固定 `mandarin_phoneme` | 即使演示切英文，也要核对适配器实际语言参数 |
| 历史选型文档 | `docs/SDK-CHOICES.md` 记录了中文失败与替换尝试，部分叙述与当前配置不同 | 视为待复核的实验记录，不直接复用其错误率或“不可用”的全局结论 |
| 任务二 | 已有交接文档以中文输入为主，输入只有四字段 | 英文演示同样要验证健康分流；不能假定任务二已支持两种语言 |

官方资料方面，NVIDIA 的 [Nemotron 3.5 ASR 模型卡](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b)将普通话 `zh-CN` 列为 broad-coverage；[MagpieTTS 模型卡](https://huggingface.co/nvidia/magpie_tts_multilingual_357m)列有中文，并给出显式 language 参数与文本归一化用法；[Riva ASR 文档](https://docs.nvidia.com/deeplearning/riva/user-guide/docs/asr/asr-overview.html)也列有普通话模型。它们说明存在中文路径，**不证明仓库当前适配代码、指定 SDK 版本、DGX 环境或老人语音已通过验证**。

## 3. 建议采用的语言策略

| 方案 | 数据流 | 建议 |
|---|---|---|
| **原语言实时路径** | 老人中文 → 支持中文的 ASR → 中文上下文与回复 → 支持中文的 TTS；API 字段保持英文 | 首选验证路径，减少额外翻译调用；具体 ASR／TTS 可通过适配器替换，是否满足赛制另核对 |
| **中文实时＋英文后台分析** | 实时保持中文；后台在授权范围内提前生成英文分析材料或索引别名 | 若分析后端确需英文，可以评估；译文保留原文来源，不拖住当前回复 |
| **英文主处理＋中文桥接** | 中文 ASR → 必要的输入翻译 → 英文处理 → 中文输出翻译 → 中文 TTS | 作为可选兼容方案，必须实测额外首音延迟、翻译准确性、流式取消和 DGX 资源竞争 |
| **全英文演示** | 英文 ASR／回复／TTS，英文记忆样例 | 仅在团队及赛事允许、参与者能理解时主动选择；不作为中文老人会话的静默降级 |

英文系统指令可以要求多语言模型直接输出中文，这是否可用由模型能力与测试决定，不必自动增加独立翻译模型。若确需桥接，先判断只需输出翻译还是输入输出均需翻译，避免无用往返。

**翻译文本无法补救中文 ASR 已经听错的内容，也无法让只支持英文的 TTS 正确读中文。** 中文产品路径仍需可用的中文输入和发声能力；方言、夹杂外语及人名地名另测，不能由普通话支持推导。

## 4. 对本 Skill 的具体约束

1. **保留原语言来源。** `text` 为原语言最终转写或直接输入，`text_locale` 标记实际文本语言；不能把翻译后的英文冒充老人原话。没有原语言转写时，不自动形成可信的个人历史记录。
2. **译文是派生内容。** 经历和证据带语言标签；需要的译文或跨语言检索别名单独关联原记录 ID、版本、翻译模型／版本、时间与复核状态，不形成第二份独立事实。
3. **个人细节优先保真。** 姓名、称谓、地名、方言词、否定、数量和模糊日期保持原样或标为未核实；不能只保存音译，更不能因译名相近自动合并人物。
4. **情绪与交流观察依赖原话。** “还行”“随便吧”等含义不能只靠英文译词判断；无法理解原语言时保留待核实状态，不升级为稳定偏好。
5. **实时检索不在线翻译。** `prepare_turn` 和 `build_context` 只返回原内容及已经存在、仍有效的语言变体；缺译文就明确报告，不偷偷调用模型突破预算。
6. **当前语言选择优先。** 会话语言与老人长期语言偏好区分；一次英文演示不自动改变本人的长期偏好。
7. **权限、更正与删除覆盖派生内容。** 译文／别名继承源记录的用途和到期时间，缓存还要检查源版本；原文撤回后不能从英文副本取回。

用户语言偏好、模型实际支持的语言与 ASR 实际检测语言分别记录。自动检测不确定时用 `und`，混合语言用 `mul`；不把会话设为中文当成每条文本都是中文的证据。

## 5. 配置与 API 对接

| 配置或字段 | 作用 |
|---|---|
| 会话 `locale` | 本次预期交流语言；现有字段保留 |
| 会话 `reply_locale` | 希望系统对老人使用的语言，省略时等于 locale |
| 轮次 `text_locale` | 实际最终文本的语言；未知为 und，不由 locale 自动填充 |
| 查询 `context_locale` | 原文之外希望获取的语言变体；默认 original；仅查询缓存变体 |
| `entries.content_locale`、`evidence.text_locale` | 原记录／证据的实际语言 |
| `entry_variants` | 可选译文表：源 ID／版本、locale、文本、翻译来源、时间、复核状态；随源记录失效 |
| `analysis.input_locales / output_locales` | 分析适配器声明的能力；启动与样例测试共同核对 |
| 部署 `language_mode` | `native / offline_analysis_bridge / interactive_bridge / english_demo`，由团队明确选择 |

ASR／TTS 型号、checkpoint、语言参数、文本归一化、SDK／运行环境和流式能力由任务一登记；主控检查整条选定路径是否匹配。健康模块按其支持的原语言处理，四字段协议保持不变；语言能力的部署选择不能依赖偷偷增加第五个字段。

需要英文桥接时，翻译适配由主控／模型层负责，本 Skill 提供可追溯内容。语音和健康负责人需验证原语言停止／拒绝／风险表达能及时处理，不能只依赖翻译后的关键词命中。远程翻译不因其用途不同就绕过数据出网许可。

## 6. 延迟与验证怎么补齐

- 分别记录 ASR final、输入翻译、主回复首 token、输出翻译首个完整语义片段、TTS 首音和客户端实际播放时间；本地翻译仍可能增加推理和排队时间。
- 中文原生、桥接、英文演示分别测试，不能拿英文延迟替代中文成绩。1.5 秒首段有意义声音仍是待协商目标；100 ms 仅为记忆检索预算，不覆盖翻译模型。
- 桥接若不支持流式，必须如实报告等待整句／整段翻译的时间。若支持流式，先形成可靠短语再播报，避免尚未出现的否定改变含义；插话时取消生成、翻译和待播放音频。
- 预缓存稳定记忆译文可以减少会话中的翻译，但缓存键必须含语言、原文版本和用途；不预生成假的聊天回答。
- 中文同义表达、英文同义表达与跨语言召回分开评估。首版关键词检索不保证任意中英互查；没有预先生成的别名或支持跨语言的后端就报告能力范围。
- 质量样例覆盖姓名／称谓、数字／日期、否定／拒绝、短句／停顿、方言词和情绪含混表达；记录 CER／WER 的归一化口径，并辅以人工听辨和关键信息核对。ASR 回读 TTS 不能单独定位到底是谁出错。

**建议审核结论：API 与数据层保持多语言兼容，优先验证原语言实时对话；英文后台及本地翻译作为可配置路径。实际演示语言与模型组合由团队基于赛制和复测决定。** 本轮只更新设计，不修改其他成员的组件。
